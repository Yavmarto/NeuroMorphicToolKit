## Overall Impression

NMTK has a coherent design language at its core. The shell chrome, workspace chips, mode tinting, and CNL editor surface read as a unified, purposeful tool — exactly the "Transparent Machine" north star. When you are inside NeuroStudio with a loaded spec file, it feels like the product it is trying to be.

The problem is coverage. The design system is applied selectively. Two instrument surfaces (Neurochip, Neurosense) look like they were built by a different team, because functionally they were — the token system is not reaching them. The result is a product that feels polished in one room and unfinished in the next, which is disorienting for any user who crosses surfaces.

The second structural gap is expert affordances. The target user is an SNN researcher or hardware engineer. Neither has patience for a tool with no keyboard shortcuts, no undo, and no command entry. The product currently asks them to operate with one hand tied behind their back.

---

## What's Working

1. **Mode palette and workspace chips.** The command/studio/instrument tinting is subtle, consistent, and effective. The chip pill shape with its 6 active-states system is the most distinctive visual signature in the codebase — it is good and should be protected.

2. **Flat elevation model.** The `elevation: 0` discipline on cards, combined with token-driven border and background tinting, produces a visual hierarchy that reads as technical without being heavy. The scanner found zero decorative shadow violations in the UI core; the violations are in the module layer, not the design system itself.

3. **CNL language bridge.** The studio screen's text-first CNL entry, paired with the canvas visualisation, is the most product-differentiated surface in the codebase. No competitor in the PRODUCT.md anti-reference list has this. It is not yet fully polished but the interaction model is correct.

## Priority Issues

### P0 — Hardcoded semantic colors in Neurosense (data loss risk in light mode)

`live_signal_viewer.dart` and `recording_controls.dart` use `Colors.red` and `Colors.green` for live signal state. These bypass the token system entirely. In NMTK's light theme, `Colors.red` on `Colors.white` produces ~2.5:1 contrast — WCAG AA failure. More importantly, the light-mode instrument user (a lab environment during daytime data collection) cannot trust their signal status readout.

**Fix:** Replace with `NmtkShellTokens.statusLive`, `.statusError`, `.statusDegraded` etc. One file each, surgical.

---

### P1a — Template gallery load has no unsaved-work guard

In `studio_screen.dart`, loading a template replaces the current CNL spec. No confirmation dialog, no draft save, no diff preview. A researcher mid-edit who accidentally taps the wrong template loses work silently. The CNL spec is the primary artifact of the product — protecting it is table-stakes.

**Fix:** Check `isDirty` state before any template-load action; show a single inline confirmation banner (not a modal — the Inline-Over-Modal Rule applies here).

---

### P1b — Three UI component libraries in active conflict inside neurocnl

`NmtkSurfaceCard`, `ShadCard`/`ShadButton`, and bare `Material` widgets coexist in the same module. This is not a visual nit — it means three different interaction models, three different focus behaviors, three different tap target sizes, and three different color contracts. Neither the hardware engineer nor the researcher persona can build a mental model of how the tool works when the tool itself does not have one.

**Fix:** Pick one (the answer is `nmtk_ui_core` — it exists for this reason) and migrate neurocnl surface by surface. The Shad components should be removed; their usage was likely a temporary scaffold.

---

### P2a — "Ownership Boundary" card repeated verbatim on 3 screens

`AnalysisScreen`, `HardwareScreen`, and Neurochip analysis all render the same explanatory card with identical text. Repetition signals that this card is doing information architecture work — explaining which module owns which function — that should be solved at the routing/navigation level, not by pasting a card everywhere.

**Fix:** Either move this content into the module's nav header as a subtitle (one sentence, always visible), or delete it from 2 of the 3 locations and trust the user to read it once.

---

### P2b — Neurochip AnalysisScreen has zero design system usage

The scanner and LLM review agree: this screen uses no `nmtk_ui_core` components. It is visually inconsistent with every other surface. Given this is a hardware-facing screen that shows chip utilisation and deploy status, it is also the screen where accurate, trustworthy visual output matters most.

**Fix:** Refactor using `NmtkSurfaceCard` (tone variants), `NmtkShellTokens` for status colors, `NmtkPrimaryButton` for deploy actions.

---

### P3 — 24 `IconButton` instances without tooltip (systematic a11y gap)

Scanner found 24 `IconButton`s with no `tooltip` parameter, distributed across `studio_screen.dart`, canvas widgets, and `nmtk/tool_view.dart`. This is a screen-reader failure and a discoverability failure for any user who does not already know what every icon does. Given the target persona (a researcher new to the tool), this is worse than usual.

**Fix:** Global pass, add `tooltip: '...'` to every `IconButton`. One afternoon of work.

## Persona Red Flags

**The PhD researcher (first session, empty canvas)**
Opens NeuroStudio, wants to write their first CNL spec. There are no empty-state instructions, no example snippets surfaced, no guided entry. H10 scored 1/4 for this reason. The researcher persona has domain knowledge but does not know the tool — NMTK currently assumes the opposite.

**The hardware engineer (deploying to Akida chip)**
Navigates to Neurochip, encounters 10 ungrouped fields on the deploy form, no keyboard navigation, no shortcut to trigger the deploy action, status feedback via `Colors.green` (which may fail contrast in their lab's ambient light). This is the highest-stakes action in the product (hardware deployment) and it has the worst UX support.

**The power user (switching between surfaces mid-session)**
Crosses from NeuroStudio to Neurosense to cross-reference a simulation against a biosignal. Hits the visual register shift (two different component libraries, mismatched elevation, different status color semantics), loses trust in the coherence of the tool. This is the scenario where P1b bites hardest.

## Minor Observations

- `studio_screen.dart` line 765 has a decorative `BoxDecoration` with an explicit shadow on a panel container. Small, but it is a named violation of the Flat-By-Default Rule and sets a precedent.
- `cnl_editor.dart` uses `elevation: 8` on its internal container. Material elevation at that value produces a visible drop shadow — inconsistent with the rest of the flat system.
- ~12 em-dashes in displayed UI strings (`—`). Easy find-and-replace pass; DESIGN.md §6 bans them explicitly.
- The server setup screen has the most explanatory copy in the entire product. That copy quality should be the baseline, not the exception.
- `NmtkMotionTokens.durationBase` (220ms) and the `tap-scale` wrapper are defined and excellent. They are not used consistently across all surfaces — Neurochip and Neurosense interactive elements have no tap feedback.

## Questions to Consider

- Is the three-library conflict in neurocnl a known technical debt or has it grown organically? Knowing this affects remediation strategy (planned migration vs. incidental accumulation).
- The CNL editor has no undo. Is this a known gap with a planned fix, or was it not prioritised yet? Undo in a text-primary tool is close to a P0 from a UX perspective.
- Are Neurochip and Neurosense intended to reach full design system coverage, or are they considered lower-priority surfaces? The answer determines whether P2b is a one-sprint fix or a longer roadmap item.
- The 21 `showDialog` calls: some of these are correct (destructive confirmations). Before any modal-reduction pass, it is worth auditing which are necessary vs. which are the path of least resistance.

## Next Steps

Three structural issues stand out from this critique, each pointing to a different command:

1. **The three-library conflict (P1b)** is a `$impeccable harden` problem — it is about making a fragile surface production-grade. Starting here unblocks everything else in neurocnl.

2. **The instrument surfaces being off-system (P0, P2b)** is a `$impeccable colorize` + `$impeccable layout` problem — Neurosense and Neurochip need the token system applied, not redesigned.

3. **The expert affordances gap (H7: 1/4)** is a `$impeccable craft keyboard-shortcuts` problem — it requires designing and building a new surface, not patching existing code.
