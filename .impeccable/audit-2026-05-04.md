## Anti-Patterns Verdict

**Does this look AI-generated?** Mostly no — the token system is intentional, the workbench mode palette separation is distinctive, the surface-tinting elevation model is correctly applied. Two specific tells:

1. **Elastic/spring animation** (`easeSpring = Curves.elasticOut`) — the logo entrance and tap-scale reverse both use elasticOut. This is the classic "AI added some bounce to make it feel alive" tell. The design law bans it explicitly.
2. **`NmtkLoadingScreen` treatment** — 64px icon in a box, large text below, progress bar — reads as a generic SaaS splash screen more than a "transparent machine" loading moment.

These are fixable. The core navigation chrome and component system do not have AI slop tells.

## Detailed Findings by Severity

### [P0] `easeSpring` token is `Curves.elasticOut` (DONE)
- **Location:** `nmtk_ui_core/lib/motion_tokens.dart:65`
- **Category:** Anti-Pattern / Performance
- **Impact:** Used in `NmtkLoadingScreen` logo entrance and `NmtkTapScaleWrapper` reverse (tap release). The logo bounces in. Tap-release springs with overshoot. Both directly violate "Ease out with exponential curves. No bounce, no elastic." Because this is a named token, every future consumer will inherit the violation.
- **Recommendation:** Replace `Curves.elasticOut` with `Curves.easeOutQuart`. The DESIGN.md doc describes "spring-back" but means the *feel* of a quick snap-back, not literal oscillation. `easeOutQuart` at 180ms delivers the same snappy reversal without bounce.
- **Suggested command:** `$impeccable animate`
- **Status:** **Fixed** (Switched to `Curves.easeOutQuart`)

### [P1] Keyboard navigation gap: `_SidebarNavItem` and `_RailIconButton`
- **Location:** `nmtk_ui_core/lib/widgets/desktop_scaffold.dart:565`, `desktop_scaffold.dart:440`
- **Category:** Accessibility
- **WCAG:** 2.1.1 Keyboard (Level A) — all functionality must be keyboard operable
- **Impact:** Both widgets use `GestureDetector` without a `Focus` widget or `onKeyEvent` handler. A keyboard user cannot reach or activate any nav item or the settings button in the desktop rail. These are the primary navigation affordances. Screen readers can announce them via `Semantics(button: true)` but cannot activate them without pointer simulation.
- **Recommendation:** Replace `GestureDetector` + `MouseRegion` with Flutter's built-in `InkWell` (which handles keyboard focus, Enter/Space activation, and visual focus ring automatically) wrapped in `Material(color: Colors.transparent)`. Or wrap the `GestureDetector` with a `FocusableActionDetector`.
- **Suggested command:** `$impeccable harden`

---

### [P1] Material theme builder always returns dark variant
- **Location:** `nmtk/neuro_toolkit/lib/main.dart:166`, `main.dart:212`
- **Category:** Theming
- **Impact:** Both `LauncherBootstrapHost` and `NeuroToolkitApp` pass `materialThemeBuilder: (_, __) => settings.isHighContrast ? AppTheme.highContrastDarkTheme : AppTheme.darkTheme`. There is no light variant path. When a user selects `ThemeMode.light`, Shadcn components correctly switch to the light Shad theme, but all Material widgets (dialogs, snackbars, `NavigationBar`, Material-sourced `ElevatedButton`, etc.) remain dark. This creates a jarring two-layer split in light mode.
- **Recommendation:** The builder receives the ambient brightness — use it: `(_, __) { final b = settings.themeMode == ThemeMode.dark ? AppTheme.darkTheme : AppTheme.lightTheme; return settings.isHighContrast ? AppTheme.highContrastDarkTheme : b; }`. `AppTheme.lightTheme` exists and just needs to be routed.
- **Suggested command:** `$impeccable harden`

### [P1] `NmtkErrorCard` hardcodes `Colors.red`
- **Location:** `nmtk_ui_core/lib/widgets/error_card.dart:29`
- **Category:** Theming / Accessibility
- **WCAG:** 1.4.3 Contrast (Level AA) — `Colors.red` (#F44336) on white at 3.98:1 fails AA (4.5:1 required)
- **Impact:** The icon and message text both use `Colors.red`. On light card backgrounds this fails contrast. On dark surfaces, `Colors.red` is not the design-system `errorColor` (`#EF4444` from `NmtkShellTokens`) and won't update with theme changes. Semantic purity rule violated.
- **Recommendation:** Replace `Colors.red` with `NmtkShellTokens.of(context).errorColor` for both the icon and the text style.
- **Suggested command:** `$impeccable harden`

### [P1] `_PipelineStep` uses `BoxShadow` on selected state
- **Location:** `nmtk_ui_core/lib/widgets/pipeline_stepper.dart:204`
- **Category:** Anti-Pattern
- **Impact:** Selected pipeline steps receive `BoxShadow(color: primary.withValues(alpha: 0.14), blurRadius: 12, offset: Offset(0, 4))`. This directly violates the design system's "Flat-By-Default Rule" and "Border-Not-Shadow Rule". A drop shadow introduces elevation that doesn't exist in the surface stacking model.
- **Recommendation:** Remove the `boxShadow` list entirely. Selected state is already communicated by `border width: 1.6` (vs 1.0) and the background tint. If more visual weight is needed, increase the border width to 2.0 or use `accentContainer` background tinting.
- **Suggested command:** `$impeccable polish`

---

### [P1] `NmtkTone.success` and `.warning` hardcode light-mode-only colors
- **Location:** `nmtk_ui_core/lib/widgets/tone.dart:35`
- **Category:** Theming / Accessibility
- **WCAG:** 1.4.3 Contrast (Level AA)
- **Impact:** `NmtkTone.success` foreground is `Color(0xFF1B5E20)` (dark green on ~12% opacity green background). On dark surfaces, a dark foreground on a near-invisible background fails contrast hard. `NmtkTone.warning` has `Color(0xFF9A5B00)` (dark amber) — same problem in dark mode. Neither color adapts with `Brightness`.
- **Recommendation:** Add a `final bool isDark = Theme.of(context).brightness == Brightness.dark` check in `resolveNmtkTonePalette`. For dark: `success.foreground = tokens.healthyColor`, `success.background = tokens.healthyColor.withValues(alpha: 0.12)`. Resolve `NmtkShellTokens` from context rather than hardcoding.
- **Suggested command:** `$impeccable harden`

### [P2] No reduced motion support
- **Location:** `nmtk_ui_core/lib/motion_tokens.dart`, `nmtk_ui_core/lib/widgets/workspace_switcher_bar.dart:132` (status dot pulse), all animated widgets
- **Category:** Accessibility
- **WCAG:** 2.3.3 Animation from Interactions (Level AAA) — PRODUCT.md explicitly calls out "reduced motion sensitivity"
- **Impact:** The pulsing `NmtkStatusDot` runs continuously on degraded/error states. The logo entrance animation, tap scale animations, and route transitions all run regardless of OS-level "Reduce Motion" setting.
- **Recommendation:** Add a `MediaQuery.of(context).disableAnimations` check in `NmtkMotionTokens` consumers. At minimum: skip the pulse animation in `NmtkStatusDot` and use `Duration.zero` in `NmtkTapScaleWrapper` when `disableAnimations` is true.
- **Suggested command:** `$impeccable harden`

### [P2] Touch targets below 44px in rail nav and workspace chips
- **Location:** `nmtk_ui_core/lib/widgets/desktop_scaffold.dart:19` (`_kNavItemHeight = 36`), `workspace_switcher_bar.dart:195` (pin/close buttons `28x28`)
- **Category:** Responsive Design / Accessibility
- **WCAG:** 2.5.5 Target Size (Level AAA), Material guidance (44dp minimum)
- **Impact:** Nav rail items are 36px tall, pin/close buttons in workspace chips are 28x28. On mobile (Android target confirmed in code), these are difficult to tap accurately.
- **Recommendation:** Bump `_kNavItemHeight` to 44. Remove `constraints: BoxConstraints.tightFor(width: 28, height: 28)` override on workspace chip icon buttons — that override explicitly defeats the default touch target.
- **Suggested command:** `$impeccable adapt`

## Patterns & Systemic Issues

1. **`GestureDetector` + `MouseRegion` as primary interaction pattern**: Used in `_SidebarNavItem`, `_RailIconButton`, `_ProfileActionRow`, `_RailProfileChip`. This pattern provides hover state and pointer cursor but no keyboard path. Flutter's `InkWell` + `Material` covers all cases at no extra cost.

2. **Tone palette not dark-mode aware**: `NmtkTone.success` and `.warning` in `tone.dart` hardcode light-mode values. The `danger` and `info` tones correctly resolve from `colorScheme`. Inconsistency means dark-mode users see light-mode colors on two of the five tone slots.

3. **Material vs. Shad layer drift**: The dual-layer theme architecture (Material 3 + Shadcn) requires both layers to stay in sync. Currently only `darkTheme` is provided to the Material builder. As the app grows, Material-sourced widgets will accumulate and the light mode gap will widen.

## Positive Findings

- **Token system is genuinely excellent.** `NmtkShellTokens` with dark/light branching at the factory, named semantic status colors with clear one-job-each rules, three workbench mode palettes — this is production-grade infrastructure.
- **Flat-by-default surface model is correctly applied everywhere except the pipeline stepper.** Zero `elevation` on cards throughout, 1px borders defining bounds — very clean.
- **Semantics coverage is good.** `Semantics(label: ..., button: true, selected: ...)` is applied to workspace chips, nav items, action buttons, error retry buttons, and module install buttons. The baseline is solid; the gaps are closures, not structural rewrites.
- **`NmtkMotionTokens` as a token file is the right call.** Centralizing durations and curves is correct architecture. It just needs the `easeSpring` value fixed.
- **`NmtkWorkspaceShell` responsive layout** using `LayoutBuilder` + flex ratios is exactly right for the two-pane workbench model.
- **Keyboard shortcuts for file operations** via `CallbackShortcuts` in `_FileActionShortcuts` — correctly handles both Mac (⌘) and Windows/Linux (Ctrl) without platform branching.
